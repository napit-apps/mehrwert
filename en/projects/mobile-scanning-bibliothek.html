PROFESSIONAL EXPERIENCE · MARCEL RUSS

An in-house barcode-scanning library for store apps

HUGO BOSS

Replace a paid software component with a native iOS solution while considering technical quality, integration and long-term dependencies together.

HUGO BOSS · Mobile retail applications · iOS

When a small component creates a lasting dependency.

Scanning barcodes and QR codes is a practical everyday function in mobile store applications. At HUGO BOSS at the time, this relied on a licensed library from an external provider.

The task was to create a suitable alternative that fitted the existing iOS applications. It was not merely about implementing the same function differently. Effort, maintainability and long-term dependency on external components also mattered.

Assess technical decisions in their product and team context.

The initiative took place during my earlier employment in HUGO BOSS's web and mobile organisation. Technical product decisions and collaboration in development were part of my responsibilities there.

The scanning library was technical work carried out by the team at that time. Such decisions show how a seemingly small function can affect licensing, integration and subsequent development.

Develop an alternative that fits existing applications.

The key was replacing the scanning function within the existing product context without turning a single component into a large modernisation initiative.

  1. 01

    Understand the dependency and requirements

    The existing scanning function depended on a paid library. Replacing it required examining the necessary functions and their integration into store applications.

  2. 02

    Provide a native scanning component

    The development team created HBScanner, an in-house iOS library for scanning barcodes and QR codes. It provided the technical alternative to the external component.

  3. 03

    Integrate into existing apps

    The new library was integrated into existing applications. This allowed the previous third-party component to be replaced and the associated licence dependency to end.

The function remains. The technical dependency changes.

A change in technical foundations need not be visible to users. It can nevertheless matter for a product's further development.

What changed in concrete terms.

An integrated in-house iOS library

HBScanner provided a native alternative that was integrated into existing store applications. Scanning remained part of the apps in use.

Less dependency on a third-party component

The external scanning library was replaced and its paid licence was no longer needed. This changed the technical dependency; responsibility for the in-house solution now rested more within the product organisation itself.

What this experience shows about today's technology decisions.

Choosing a library may seem minor. Over the years, however, it affects how independently a product can evolve, what costs arise and who must resolve problems.

At mehr.wert, we therefore consider these decisions in context: what fits the application over time, what risks does a dependency create, and when does it make sense to take responsibility for a component ourselves?

Are you facing a difficult technology or vendor decision?

Whether an existing library, standard software or an in-house solution, we help assess alternatives objectively and align decisions with actual requirements.
